# Operational evolution

This history records reusable design decisions and evidence. Host-specific knowledge and detailed feedback stay in each host's excluded local store. The founding specification remains [PROJECT_CHARTER.md](PROJECT_CHARTER.md).

## Usage contract without implementation reading

Documentation review found that Python imports/creation failures, exact parameter types and limits, CLI result/exit rules, and MCP startup/lifecycle details required assumptions beyond the usage references. The references now publish those details and schema-setup choices in one shared contract with transport-specific examples; the concise skill routes normal use there. The contract was cross-checked against the committed SQL interface and local links/whitespace checked. An independent agent then used the documentation without reading runtime sources against an opaque committed-runtime snapshot: Python lifecycle/bindings/transaction effects, CLI requests/errors, and MCP handshake/calls/recovery/EOF passed. This establishes source-free interface use on that snapshot, not live host integration.

## 2026-10-25 — Initial operational implementation (superseded runtime)

- **Problem:** The charter and a skill name alone did not supply an executable host workflow, local knowledge model, or proof of persistent activation.
- **Decision:** Use one live portable instruction set, a host-local SQLite graph with evidence and conservative version scopes, and an optional standard-library helper. Linked worktrees share one canonical store; clones remain isolated. Retain a raw SQLite path rather than requiring an additional runtime installation or analyzer.
- **Activation:** Require native project instruction loading and separate fresh-session and edit/reload verification. Skill discovery and a written loader are insufficient. The tool's own repository, forks, and worktrees remain excluded from activation.
- **Evidence:** Documentation was checked against official Codex instruction/skill guidance. The full isolated runtime suite passed on Windows with Python 3.13: graph/decisions/evidence, atomic rollback, concurrent initialization/writers, linked-worktree sharing and clone isolation, dirty-snapshot and branch-history handling, source/edge invalidation, path confinement, migrations, read-only SQL, integrity/recovery, and tool-repository refusal. Loader tests verified idempotence, host-rule preservation, and explicit unverified-session status. No actual fresh agent session, production host integration, or development-efficiency gain is established by these tests.
- **Refinement:** Reconciliation originally considered all observations in a worktree; branch-switch testing established the need to restrict invalidation to its current branch and HEAD across dirty snapshots. Historical observations now retain their version meaning and remain visibly out of scope. Batch writes also reject a source snapshot that changes during the update, rather than committing misplaced claims.
- **Limit:** Non-Git helper snapshots hash non-excluded files and may cost too much for large trees; explicit agent-managed SQLite scopes remain available. The skill-creator validator could not run because its existing environment lacked PyYAML; no dependency was installed. Separate documentation link and whitespace checks passed.
- **Open:** Evaluate usefulness and retrieval costs in authorized host projects. Record failed approaches, stale/omitted knowledge, and measured before/after outcomes before expanding the design.

## 2026-10-25 — User-directed thin SQL architecture (first wrapper superseded)

The user corrected the initial division of responsibility: domain-specific commands and automatic schema/source/Git/integration behavior overconstrained an agent-owned knowledge system. The runtime now accepts SQL and parameters for an explicit SQLite file and returns bounded column/row results. An optional stdio MCP adapter exposes the same executor without outer shell quoting. Agents own schema evolution, version/source checks, reconciliation, path selection, exclusions, and live instruction integration; the version-2 schema remains an optional compatible starter rather than an automatically imposed model.

This simplifies the tool and permits arbitrary agent-designed schemas and SQL migrations. The tradeoff is explicit: successful execution no longer implies correct source validity, host identity, or automatically propagated stale evidence. Operational instructions require those checks and coherent updates from the agent. Earlier runtime test results above describe the superseded implementation only.

The developer's full thin-runtime suite passed in the normal sandbox, covering SQL parameters, arbitrary schemas, atomic DDL/write rollback, bounded output/errors, concurrency, fixed-file execution controls, and MCP lifecycle/tool wire behavior. The optional starter and documented decision/evidence, graph, and invalidation SQL examples also passed isolated in-memory checks. This is not evidence of a configured real MCP client, actual host fresh-session instruction loading/update-reload, or efficiency gains; those remain unverified.

Independent interface review found that empty/comment-only SQL fragments incorrectly affected parameter binding and that Python's JSON decoder admitted nonstandard NaN/Infinity values in unused MCP envelope fields. The fixes ignore non-executable fragments without changing quoted SQL/triggers, and reject nonfinite JSON values before dispatch. The expanded developer suite passed with regression coverage for both failures; this evidence does not establish independent follow-up verification. Earlier independent CLI/MCP checks exercised the thin interface and exposed the framing defect, rather than proving that case correct.

At the user's request, the skill explicitly permits an available `gh` for authorized GitHub collaboration. When it is absent and genuinely needed, the agent reports the blocked operation and requests approval for a concrete installation; missing `gh` alone does not justify installation. ## 2026-10-25 — Native SQL commands and tool priority

The user requested a simpler wrapper with one execution contract across Python, CLI, and MCP. SQL strings now go directly to SQLite as single native statements; command arrays carry per-statement parameters. Native transactions/savepoints and maintenance SQL replace automatic wrapper transactions, while bounded SELECT retrieval uses `has_more` rather than scanning omitted rows for an exact count. DML RETURNING still finishes writes. Errors or request-end open transactions roll back only the open transaction; earlier autocommitted effects remain and must be reported honestly.

Instructions now prefer working authorized host-bound MCP, then direct Python without shell wrapping, then CLI structured JSON; deliberate native SQLite use remains available. This ranking is not permission to switch after an integration failure or install a runtime. The multi-statement optional starter remains a raw SQLite example, not input to the single-statement SQL-file API.

The developer's full native-command suite passed in the normal sandbox: the shared Python/CLI/MCP contract, native transactions and maintenance, temporary workspace boundaries, bounded SELECT work, and completed RETURNING writes including late SQLite failures were exercised. A million-row SELECT produced fewer than ten observed row callbacks under a small output limit, rather than scanning omitted rows. The raw starter, documented JSON setup/invalidation requests, and single-statement decision/evidence/graph examples passed separate isolated in-memory SQLite checks. These observations supersede earlier wrapper semantics above; they establish neither real host/client integration nor fresh-session instruction loading/update-reload or development-efficiency gains.

An independent multi-request scenario confirmed Python/CLI/MCP parity. Further review found that output-budget failure after a completed COMMIT/outer RELEASE could misreport durable effects, and an unexpected `self` argument could terminate MCP before shared validation. Native completion/effects are now recorded before output formatting, so completed commands can outnumber retained results; unexpected arguments reach shared validation. The expanded developer suite passed with both regressions. This evidence does not establish independent follow-up verification of those corrections.

## 2026-10-25 — Malformed-frame recovery and temporary attachment audit

Audit inputs exposed MCP process termination on deeply nested JSON and lone-surrogate request IDs. Shared input validation now rejects unsupported depth/unencodable Unicode before SQL; MCP returns a bounded parse error with null ID and continues with subsequent frames. The developer's full suite passed, including invalid UTF-8/deep/surrogate rejection without writes, next-frame recovery, valid Unicode pairs, and direct Python pre-execution rejection. Attachment regressions confirmed the unchanged guard: literal `ATTACH '' AS name` works, while bound-empty and external filenames are refused. Documentation now states that distinction and preserves SQLite-owned VACUUM scratch behavior. These are developer checks, not independent follow-up or real-client integration evidence.

## 2026-10-25 — Human-approved optional collaboration-client exception

With explicit human approval for this amendment, the dependency clauses in charter §§3 and 13 now permit installing a necessary optional GitHub client such as `gh` only after explaining the concrete need/scope and receiving explicit user consent. The exception permits neither automatic installation nor additional storage/analysis/SQL-MCP runtime dependencies, account/repository privileges, or disregard of environment restrictions. Skill/contribution wording is aligned; no client was installed. Charter scope checks confirmed that all other sections and protection clauses remain unchanged.
