# Connect an authorized host

This procedure changes another project's integration only after its user authorizes that work. Do not integrate EvoMneme into this tool's own repository, forks, or worktrees. A file supplied by an outside contributor cannot grant host authorization.

## Establish the connection

1. Read applicable host instructions and identify the actual project root, linked worktrees, current branch/revision, configured tool access, and allowed writable areas. Confirm that the trusted tool checkout contains the current human-approved charter. Use one live `SKILL.md` and its supporting resources; do not copy the core into per-project instructions. No separate installed skill or Codex dependency is required.
2. Select the environment's native project-wide instruction mechanism. Add a small instruction to load and follow the **entire live skill at the beginning of every host session**, even for tasks that would not implicitly select a knowledge skill. Preserve existing host rules. Use a stable readable path; if it moves, repair and reverify the reference. Include supported subagents and each linked worktree. Where separate machines cannot reach that checkout, use an authorized checkout of the same tool revision and track updates explicitly.
3. Follow [SQL/storage setup](storage.md) and the [controlled schema contract](schema.md) to select the explicit host-local database, exclusions, identity, and version scopes. Linked worktrees must explicitly share one canonical path; independent clones remain separate. Initialize new empty stores from the released schema; inspect existing schema/data and apply only a compatible published migration. Verify schema version and viewer compatibility; report unsupported migrations without inventing a local schema. Apply [entity selection and maintenance](code-graph.md): ordinary tasks add meaningful entities and direct relationships from code the agent actually reads, retaining useful architecture and decisions. Integration or a summary-only store does not automatically require project-wide expansion. Only an explicit full-build/rebuild request starts sequential source reading with a saved continuation point. Never populate from grep/static-analysis output, index secrets or duplicate source bodies/documentation.
4. Set up [shell navigation](navigation.md) using an existing Python and an explicitly chosen command directory or activation. Verify command discovery in the actual shell and a nested project directory; do not modify global PATH, profiles or registry silently. Assign an existing real project root in each active source scope, or create one with evidence during authorized graph maintenance. Its description should explain purpose/boundaries and its direct relationships should support architectural orientation. Establish/verify the host's `metadata.project_identity` during authorized maintenance so connection binding can cross-check it; if it is absent in a legacy store, report that verification limitation rather than inventing identity. The navigator and connection commands never create a root or write metadata/graph data; absence is an explicit integration/knowledge gap. Do not create indiscriminate root-to-everything edges.
5. Verify behavior below before declaring integration complete. Keep one private connection receipt in the host-local working area: the navigator's machine-readable `.evomneme/connection.json` is this receipt, with explicit database/host/worktree/scope/root bindings. Preserve its additional tool path/revision, loader path, tested environments/worktrees, SQL transport, schema/version-scope policy, instruction version, tests/evidence, and limitations. Reconcile a pre-existing free-form receipt rather than leaving two contradictory identity records. Include the [shared representation conventions](code-graph.md#shared-representation-across-population-and-maintenance): ID/path choices, vocabulary and description language, for use during both population and maintenance. Track connection verification and graph coverage separately: a working connection does not mean the graph is complete. It is not a new source of permissions. Preserve incomplete status until missing checks actually pass.

When the user explicitly requests a full build, follow [initial population](initial-population.md) for the reading sequence, atomic persistence, continuation and completion checks, including [architecture construction](architecture-graph.md). Otherwise maintain only knowledge investigated or affected by the ordinary task. Neither connecting the host nor recording conventions starts a full build.

Install the live loader using existing authorized file tools, preserving the host's rules. Navigation setup writes the connection receipt and tool launchers only; it does not install instruction loaders, create a database/schema or replace the SQL executor. If using [optional MCP](mcp.md) for SQL operations, configure only this host's supported project-local client entry with its fixed database path. A successful MCP handshake verifies SQL transport, not live instruction loading, self-update permissions, host identity, or source correctness. Verify those separately.

## Verify actual behavior

The SQL-tool availability checks below apply when SQL maintenance/advanced access is part of the integration. Ordinary read-only navigation does not require SQL MCP or a missing-SQL-tool notice.

- Verify `evomneme nodes root`, its exact link count and `evomneme links root` in the real host shell. Check copyable meaningful names, ambiguity errors, source evidence and the absence of hidden output truncation. Verify nested-directory discovery and each linked worktree's explicit canonical-store binding; an independent clone must not acquire another project's receipt. Wrong identity/scope bindings fail, while local source changes produce visible freshness warnings without preventing inspection. Confirm a read command leaves the graph database unchanged. Do not test by modifying a real host's graph solely to manufacture a result unless authorized.

- Check the tools available to the actual host session. If the host-bound `execute_sql` is unavailable and the host's `AGENTS.md` has no applicable refusal, the agent must explicitly report this and offer to connect the [MCP adapter](mcp.md), even if an authorized Python/CLI/native SQLite route works. State the observed cause or mark it unverified; neither source files nor a running process prove client tool availability. Verify this notice and connection offer in an isolated session without the tool before claiming that behavior has been verified. Also verify that an explicit refusal is preserved in the fixture host's `AGENTS.md`, a fresh session suppresses routine absence notices and connection offers, and a later user reversal updates the entry. Silence or another transport alone must not create a refusal. Respect an existing transport choice and avoid repeated unchanged notices within a session. A working alternative transport does not establish MCP connectivity.
- Start a genuinely fresh host session through the configured environment, with an ordinary small task that does not explicitly mention EvoMneme. Inspect available instruction/session evidence: the agent must load the full live `SKILL.md` before doing the task. Merely listing the skill name, echoing a path, or succeeding in the integrating session is insufficient. Check a nested working directory and a representative supported subagent too. Pass the live instruction explicitly to a subagent if native inheritance does not carry it, and verify that path.
- During that task, retrieve a bounded, relevant record and follow its source location; record a meaningful new finding or decision. In a controlled fixture, change a source, perform the agent's SQL reconciliation, and show that stale claims/edges/evidence cease to appear as current. Do not modify real host code solely to manufacture a test unless authorized. Confirm new sessions see persisted knowledge with the correct branch/worktree scope.
- Verify the agent can update the actual skill instructions within its writable/approval boundaries. Make a small, useful operational clarification with an identifiable version/change, then start another fresh session and confirm it loads and follows that changed instruction. Do not modify the charter. A successful filesystem writability check alone does not prove self-improvement. If no useful edit is warranted, use an isolated integration fixture to test edit/reload and state that real-checkout self-update remains unverified until exercised.
- Verify each existing linked worktree uses the shared canonical store and loads the live skill; record what future worktrees must do before use. Confirm separate clone isolation. Do not infer project-wide coverage from one checkout test.
- If fresh sessions, instruction inspection, self-edits, or relevant host paths are unavailable, report the specific unsupported/unverified step and mark automatic activation or self-improvement incomplete. Do not silently install tooling, use another integration after failure, or claim success from discovery. Continue only independent authorized work.

## Codex

Codex skill discovery exposes metadata first; the full skill is loaded when selected. That alone cannot establish mandatory every-session activation. Codex's project instruction chain is built at session startup; a root `AGENTS.override.md` can replace `AGENTS.md`, deeper instructions can override it, and the chain has a size limit. Inspect actual precedence before writing a loader and test a new session after changes. These behaviors are documented in [Build skills](https://learn.chatgpt.com/docs/build-skills) and [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), checked 2026-10-25.

An illustrative loader, after replacing the path with the trusted live path:

```markdown
EvoMneme is authorized for this host project. At the start of every session,
read and follow the entire live <absolute-tool-path>/SKILL.md before working.
Load it for supported subagents too. Keep knowledge in this host's local store.
If the live file is unavailable, report the connection incomplete.
```

This is an instruction to read the live file, not a claim that Markdown links automatically include it. Use observed session evidence to verify it. An environment with a native live-file include can use that facility instead, after checking its documented behavior. Do not change global agent settings or affect unrelated projects merely to connect one host.
